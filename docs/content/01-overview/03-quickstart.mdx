# Quickstart

Get your first verified branch with NIKI in under five minutes.

There are two paths. **Path A needs no API key, no account and no container
runtime** — it uses a local model and the git-worktree backend, and it is the
one to start with. Path B adds container isolation and hosted models, and is
worth reading once Path A works.

<Callout type="tip">
  Everything on Path A runs on your own machine with your own keys. There is no
  account, no telemetry, and no cost.
</Callout>

---

## Path A · Zero setup (about two minutes)

### Prerequisites

1. **git, node, npm, python3, curl** on your `PATH`. The sandbox preflight
   requires all four, and the starter's `run.sh` checks them for you.
2. **[Ollama](https://ollama.com)**, running, with one coding model pulled.
3. **NIKI** — `brew install niki`, or the install script.

### Step 1 · Create your project

```bash
mkdir my-app && cd my-app && git init
```

### Step 2 · Pull a model

```bash
ollama pull qwen2.5-coder:7b
```

> **On model size.** Every stage must emit a JSON artifact matching a strict
> schema, and the Coder's is a diff expressed as search-and-replace pairs. That
> is harder than it sounds, and small models frequently cannot. `qwen2.5-coder:3b`
> fails at the Coder stage on ordinary tasks; 7b works sometimes; 14b is
> comfortable. `niki smoke` will tell you where your own model stops.

### Step 3 · Configure

```bash
niki init --interactive
```

The wizard probes your machine. It offers Ollama first because it needs no key,
and it writes a `[docker] backend` line matching what you actually have — so
there is no flag to remember for every later run.

### Step 4 · Run your first task

```bash
niki run "Add a GET /health endpoint returning { status: 'ok', uptime }"
```

Watch the pipeline execute across all four stages:

```text
 ◈ ⟠ ◉ ◆   NIKI
   "Add a GET /health endpoint…"

 [Planner]   Done — Spec: 1 file to modify
 [Coder]     Done — Changed 1 file · src/api.rs [modified]
 [Tester]    Done — 8/8 tests passed
 [Reviewer]  Done — Approved · correctness 10/10 · quality 9/10 · coverage 10/10
 [NIKI]      Task complete — Branch: niki/6d281d6d · Verdict: Approved · Revisions: 0
```

### Step 5 · Read the result

```bash
niki report 6d281d6d
```

Then look at the branch:

```bash
git -C ./my-app switch niki/6d281d6d
```

Your working branch is not modified. NIKI commits to a new branch and leaves
your tree alone, so `git checkout .` is always available.

## Path B · Container isolation and hosted models

For real work on a repository you did not write, add container isolation and a
hosted model.

### Prerequisites

1. **[Rust](https://www.rust-lang.org/tools/install) (1.88+)** — only to build
   from source. Released binaries need no Rust.
2. **[Podman](https://podman.io)** (recommended) or
   **[Docker](https://docs.docker.com/get-docker/)**.
3. An **API key** for one LLM provider, or a local Ollama.

### Step 1 · Build the sandbox image

```bash
podman build -t niki-sandbox:24.04 -f docker/Dockerfile .
```

### Step 2 · Point NIKI at the container backend

`niki init --interactive` writes this when it finds a container runtime. To
switch an existing config, set it directly:

```toml
[docker]
backend = "docker"
```

### Step 3 · Set a key

```bash
export ANTHROPIC_API_KEY=sk-ant-...
# or OPENAI_API_KEY, GOOGLE_API_KEY, OPENROUTER_API_KEY
```

Environment variables take precedence over `niki.toml`, so a key never has to
be committed. `niki init --interactive` offers to store it in your OS keyring
instead.

### Step 4 · Plan first, if you like

```bash
niki plan "Add a GET /health endpoint" --project ./my-app
niki run --plan <id> --project ./my-app
```

`niki plan` researches without changing anything and writes a reviewable
`plan.md`. Approve it, then execute it.

## If something goes wrong

```bash
niki doctor    # check install, config, providers, sandbox
niki smoke     # run a trivial task end to end
```

`niki doctor` reports your sandbox backend *against your machine*, so a
worktree install is not reported as a broken container install. `niki smoke`
runs the backend your config actually selects.

For the three failures you are most likely to hit, and the exact command that
fixes each, see the handover starter's
[TROUBLESHOOTING.md](https://github.com/RavaniRoshan/niki/blob/master/niki-starter/TROUBLESHOOTING.md).

## One command, end to end

If you would rather not set anything up, clone the starter and run its script.
It preflights the machine, shows the failing test before the run, runs the
pipeline, and explains whatever happened:

```bash
git clone https://github.com/RavaniRoshan/niki && cd niki/niki-starter
./run.sh
```
